# 常见问题：从现象找到下一步

先明确错误发生在本地、Notebook 还是正式训练容器，再关联本次作业、入口、源码版本和日志。历史相同报错只是线索，当前 traceback 和配置决定处理。

SSH 的网络、指纹、密钥与认证分层见 [ssh.md](ssh.md)；没有 SSH 可沿 [non-ssh.md](non-ssh.md) 继续。平台共用流程见 [workflow.md](workflow.md)。

## 1. 先取得最小证据

1. 记录本次实例或作业/批次，确认所读日志属于这次运行。
2. 找到首个真实 Shell 错误或 Python traceback，保留前后上下文。
3. 记录实际 Python、入口和解析后的配置；不能只看源码模板。
4. 确认最后完成阶段、仍在写入的进程/作业和已经生成的有效产物。

已有任务授权内直接做必要只读核查和限定修复。信息不足时只补问决定下一步的日志或目标，不要求用户重述平台全部背景。

## 2. 平台与 Notebook

| 现象 | 最短核查与处理 |
|---|---|
| 找不到项目、文件或资源池 | 确认当前租户/工作空间、所属课题和资源授权，再核对目标实例 |
| 创建 Notebook 时规格不可选 | 查配额、资源池租户授权、镜像架构与规格兼容性；按平台提示联系对应管理员 |
| 没有 SSH 开关 | 使用网页 Terminal；需要直连时再核实该部署是否启用此功能 |
| Notebook 长时间启动中 | 查看当前启动日志中的首个失败或仍在进行的安装/挂载阶段，不反复新建同名实例 |
| 连接曾成功，今天失败 | 核对实例是否运行、自动关闭、停启后入口和凭据是否变化，再按 SSH 分层诊断 |
| 文件面板内容与终端不一致 | 在面板对应目录打开 Terminal，运行 `pwd -P`；确认是不是不同根目录或挂载 |
| 只看到 Notebook 的一张卡 | 这只反映 Notebook 资源；正式作业卡数到作业资源与启动日志中确认 |

资源占用与项目预算分开处理。为了让界面可选而改变样本数、训练轮数或实验矩阵，需要按项目目标明确记录，不能作为无损部署修复。

## 3. 启动与参数解析

| 现象 | 原因线索与处理 |
|---|---|
| 代码下载完成后立刻退出 | 入口可能尚未开始计算，查后面的第一条真实错误 |
| `Unknown option: --checkpoint_url=""` | 某些部署空表单仍注入平台存储参数；取得实际 argv，区分平台参数与业务参数 |
| URL 参数修好后又报 CONFIG | 组合回归不完整；用本次混合 argv 测试存储参数与配置参数 |
| 配置值含多余引号 | 平台可能把一对外层引号作为字面内容传入；只按参数契约去掉匹配外层引号 |
| 新入口读到旧配置 | 复制旧表单留下 CONFIG 或其他覆盖；核对新入口默认与最终解析值 |
| “缺少参数值”但表单看起来有值 | 检查等号形式与双 token 形式、空字符串、引号是否保持，避免仅看展示文本 |
| 未知业务选项拼错却被忽略 | 平台兼容参数应单独登记，未知业务选项仍应报错，不能统一忽略所有参数 |
| 入口帮助或预检也触发训练 | 先检查入口实现；不要反复试未实现的 `--dry-run` 等选项 |

维护自有入口时，可按实际平台需求兼容 `CONFIG/config/--CONFIG/--config`、等号与双 token、CLI 最后值覆盖和空值回默认。第三方入口先核实际契约；不通过 `eval` 解析用户字符串。

启动解析失败通常不产生本轮有效训练状态。不要因此自动加恢复开关，或把旧权重当作这次已经训练的证据。

## 4. 路径、Python 与运行时

| 现象 | 最短核查与处理 |
|---|---|
| `can't open file ...` | 先 `pwd -P`、确认项目根和入口存在，再用正确绝对路径或切到项目根 |
| 本地有脚本，远端报不存在 | 通过上传、SFTP 或完整自含补丁传过去；本地保存不等于远端已安装 |
| `No module named ...` | 查本次 Python、实际源码根、包安装和 `sys.path`，再决定补依赖 |
| activation 前可导入，之后失败 | activation 可能重建 `PYTHONPATH`；激活后恢复当前源码路径并检查模块真实来源 |
| Notebook 可运行，正式作业失败 | 比较两个容器的解释器、环境、挂载和代码快照；终端临时 `export` 未必带入正式作业 |
| traceback 出现其他环境路径 | 核对实际激活脚本、解释器及已登记复用来源；可能是合法复用，也可能是污染 |
| 模型本地路径被识别为远程仓库 | 查路径大小写、解析后的真实目录和必要模型/分词器文件 |
| 依赖检查缺包 | 先确认没用错 Python；再修项目隔离环境，不直接升级全局框架与驱动 |
| Notebook 改码后仍看到旧错误 | 核对提交时源码快照、选中的代码目录和补丁回执，再从正确版本提交 |
| 修改后 manifest 不一致 | 保留原发布清单，用补丁回执说明前后摘要；不要把旧清单改成“原件未变” |

导入验证应使用正式入口同一解释器、实际 activation 和可能的非项目工作目录。仅打印命令、给探针临时加路径或使用假解释器，不能证明正式模块能导入。

## 5. 测试、计算进度与卡利用率

| 现象 | 最短核查与处理 |
|---|---|
| 任务已领取但仍为零 step | 看阶段顺序和 worker 日志，可能正在准备数据或初始验证 |
| 多卡资源却只看到几条 `WORKER_START` | 先读取完整启动区间，排除日志截尾，再核对各角色和各 rank 的日志 |
| 只有部分卡忙 | 查实际任务数、任务角色、独立槽位/helper/DDP调度，不从卡数推断实现 |
| 显存常驻但 AICore 低 | 结合阶段、CPU执行、I/O与队列；模型在显存中不代表持续计算 |
| 显存低或只有心跳 | 对照平台状态及两次实际 step/产物变化，不能凭显存判卡死 |
| batch 上限很大，实际仍很小 | 看数据组织、逐题调用、padding和token预算；增大上限不会自动跨任务拼批 |
| 明确 NPU OOM | 保留失败阶段、输入长度、实际批大小与峰值；按项目约束调整物理批和累积 |
| helper 有注册文件却无请求 | 查就绪、started/completed/failed事件和实际进程；文件存在不证明存活 |
| 已到最后 step，作业仍运行 | 查末次验证、刷新、评测、导出和报告，最后一次 metrics 可能早于这些阶段 |

Notebook 内运行的小型训练能验证相应操作链路；它不能替代独立训练作业、真实模型或多卡运行的验收。

吞吐调优时保留有效 batch、任务样本数和训练预算。改变物理分组、候选调度或 RNG 可能影响结果，按项目要求记录新执行身份。OOM 后不静默缩批并重采，除非该行为已明确设计并留证。

## 6. ETA 与完成状态

| 现象 | 正确解释与处理 |
|---|---|
| 监控显示 ETA 待校准 | 对应阶段还没有实际耗时；先等待有效样本，不伪造精确结束时间 |
| 并行任务 ETA 被直接相加 | 按资源和依赖估计关键路径，普通并行任务通常看最慢剩余任务 |
| 训练倒计时归零，全流程未结束 | 最终评测/路线库/报告可能未计入；分别报告训练与全流程 |
| 完成文件存在但结果缺项 | 同时保留完成声明与完整性缺口，检查真实产物和收尾步骤 |
| 旧摘要比当前 metadata 更早 | 沿当次运行读实际状态、日志和队列，不把旧汇总当当前完成 |
| 平台已成功但分析包不完整 | 作业终态与分析证据完整性分别检查，补导出已存在的必要记录 |

平台状态、任务调度、实际计算推进与产物完整性四者相互补充。一个标记通过不自动替代其他三个。

## 7. 补丁、恢复与连接中断

| 现象 | 最短核查与处理 |
|---|---|
| `PREIMAGE_MISMATCH` | 收集真实目标文件、摘要和差异，基于远端版本合并；保留原备份 |
| 重复安装同一补丁 | 识别已安装的正确后像并报告，不重复改写或制造新结果 |
| claim/lock 残留 | 核对同一输出全部 writer 与平台批次，确认无活动写入后再按项目恢复规则处理 |
| 训练完成、收尾登记失败 | 优先审计已有有效产物能否补登记，不默认重训 |
| 页面点击提交超时 | 先查列表和批次 ID，确认是否已经创建，避免连续重复提交 |
| Ctrl+C 后平台仍运行 | 很可能只停止了监控；需要停止训练时走实际作业控制 |
| SSH断开或网页关闭 | 先查询正式作业状态；连接中断不证明训练停止，也不自动授权重提 |

恢复针对明确运行和已理解的失败原因，保留数据、配置与源码兼容性。不要通过清空输出、伪造完成文件、空模型或改预期摘要来让检查通过。

## 8. 跨端粘贴与网页文件

| 现象 | 最短核查与处理 |
|---|---|
| Terminal 粘贴后 Shift+Enter 无反应 | Terminal 普通 Enter 执行；代码单元才使用 Shift+Enter |
| 始终显示 `>` 续行提示 | 检查引号与 here-document 结束标记，结束行要完整且独占一行 |
| 中文乱码并出现字符串语法错 | 本地读取显式 UTF-8，改用 ASCII 执行封装；规范换行后校验摘要并编译 |
| Bash 命令在 Windows 报错 | 确认命令标注的执行位置；远端 Bash 与本地 PowerShell 分开 |
| 生成的文件网页中不可见 | 在文件面板对应目录开 Terminal 查 `pwd -P`，把归档复制到确认可见的目录 |
| 网页大文件传输失败 | 核对部署限制；按已授权方式改用对象存储或SSH传明确文件，保留原件 |

粘贴式补丁要完整自含，包含新增文件内容。不能让新用户先在远端运行一个还只存在于本地的安装脚本。

## 9. 打包与结果下载

| 现象 | 最短核查与处理 |
|---|---|
| 不含权重，仍打包数百万小文件 | 改为明确 manifest/allowlist，同时限制枚举、文件打开数和归档成员数 |
| 压缩包不大但打包很慢 | 元数据和小文件打开可能是瓶颈；只合并 tar 成员不一定减少源读取 |
| 大 gzip 解压后内存超限 | 流式复制压缩原件或按需要解析，不远端全量载入大面板 |
| 导出成功但原始样本为空 | 检查 expected/actual、遗漏清单与raw预算，不只看退出码和归档存在 |
| 下载 SHA 不一致 | 保留两端摘要与长度，重新传准确文件，不重写摘要文件“修复”匹配 |
| 包引用了未包含的外部文件 | 列出依赖与对分析的影响，补必要闭包或明确该包仅支持部分分析 |
| 空间不足想清旧包 | 区分下载副本、临时归档与真实实验目录；只清理明确授权的准确对象 |

结果包验收保留实际文件/样本覆盖、必要原始输出、身份、配置、日志及 SHA。记录不足时说明还能支持什么分析，不以“保守”名义丢失本来可以完整保留的证据。
